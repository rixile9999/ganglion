# Ganglion 인터페이스·피드백 개선 통합 제안 — 파일을 이음새로 삼는 운영 콘솔

> **상태:** 제안(구현 전). 원 요구 문서는 [`docs/refine.md`](refine.md). 작성일 2026-09-15. 4개 관점의 독립 제안 → 3인 심사 → 종합 → 코드 대조 검증(사실 주장 30건) → 반론 반영 순서로 작성했으며, 본문의 파일·줄번호는 이 시점의 작업 트리 기준이다.

*4개 제안(MVP 엔지니어 / 연구가치 우선 / 아키텍처 순수성 / 일일 운영자 UX)과 3개 심사 의견을 하나로 합친 문서의 **최종 편집본**. 심사 합계 1위인 제안 1(MVP)을 뼈대로 삼고 나머지 셋의 공통 지목 아이디어를 접붙였으며, 이번 편집에서 (a) 30건의 사실 주장 검증 결과, (b) refine.md 완결성 심사, (c) 엔지니어링·ML-soundness 두 렌즈의 반론을 반영했다. 기존 코드에 관한 서술은 모두 이 세션에서 직접 확인한 파일·줄번호를 따른다. 새로 만드는 모듈은 **[신규]**로 표시한다. 형식화 문서 인용(정의 n / 명제 n)은 `docs/pipeline_formalization.md`, 구현 주석 인용은 `docs/pipeline_formalization_impl.md`, 논문 인용은 `docs/paper/ganglion_mlsys_draft.md`를 가리킨다.*

## 1. 요약

1. refine.md의 여섯 항목(R1.0/R1.1/R1.2/R2.1/R2.2/R3)은 **이미 존재하고 테스트된 프리미티브 위에 얇은 어댑터 하나**를 얹으면 된다: `ModelClient.invoke`, `Catalog.render_json_dsl/render_openai_tools`, `TraceStore`, `classify_traces`, `synthesize_rules`, `summarize`, `write_report`. 단, 어댑터를 얹기 전에 **기판 수정 PR 하나(§3.0b)** 가 선행해야 한다: 현재 생산 경로는 검증 실패 추론의 raw를 버리고(`benchmarks/iot/runner.py:57-65`, `analyzer/repair.py:86-90`), 분류기의 인자 matcher는 검증된 `trace.plan`만 읽으므로(`analyzer/taxonomy.py:296-298`) 실제 실패 트레이스에서 규칙 제안·F⁰/Fᴷ 귀속·실패형 히스토그램이 전부 빈 결과를 낸다.
2. 백엔드는 **표준 라이브러리 `http.server` 기반 `ganglion/console/` [신규]** 하나이며, 새 런타임 의존성은 없다. 모든 새 레코드(라벨·패치 결정·보정 귀속·런 매니페스트·비교 결과·이벤트)는 이미 스펙된 `runs/traces/<catalog_id>/<run_id>/` 트리 안에 **추가 전용 사이드카**로만 쌓이고, 목록·조회의 SSOT는 ledger가 아니라 **파일(`manifest.json`+사이드카)** 이다.
3. 미결이던 events-vs-artifacts 이음새는 정의로 해소한다: **이벤트 = 아티팩트를 경로로 참조하는 추가 전용 ledger 행**. 행은 런 디렉터리의 `events.jsonl`에 남고(런과 함께 커밋), 전역 `runs/ledger/index.jsonl`은 재생성 가능한 파생 색인이다. 인프로세스 버스·SQLite·FastAPI는 이번 사이클에 도입하지 않고 이름만 예약한다.
4. R2.2는 **확장(제안 → 블라인드 인간 결정 ledger → 검토된 코드 편집으로 이식)** 과 **축소(저장된 raw의 첫 시도를 F⁰/Fᴷ로 재파싱해 hook 종류별 Rescue/Regression을 귀속 → 통계적 흡수 판정 → retire 결정)** 로 분리한다. "분석기는 제안만 하고 사람이 적용한다"는 논문의 경계는 그대로 둔다.
5. refine.md의 "RLHF"는 보상 모델도 선호 최적화도 아닌 **교정 SFT(corrected-SFT)** 로 구현한다. 인간 라벨에서 DPO 쌍을 직접 만들지 않는다(off-policy 정규형 문자열 vs 모델 raw는 DPO 설정이 아니다 — `docs/pipeline_formalization_impl.md:517`, `docs/tasks/lm_finetune.md:30-34`).
6. 이 콘솔은 MLSys 초고가 비워 둔 측정치(proposer precision/recall vs operator rules, 규칙 은퇴, 다중 반복 ledger, human minutes, 오염 제외 재실행)를 **일상 운영의 부산물로 생산**하도록 설계하되, 그 측정이 주장으로 성립하기 위한 **측정 프로토콜(§3.7)** 을 P2 착수 전에 스펙으로 고정한다. Phase 0~4, 총 **12개** 신규 태스크 스펙.

**라벨 순환성 방지(ML 반론 #2).** 라벨러가 보정 후 plan(Fᴷ)만 보고 "정답"이라 하면 gold := Fᴷ(y)가 되어 Rescue가 자동 1, Regression은 관측 불가가 된다. 그래서 F⁰(y)≠Fᴷ(y)인 카드는 두 plan을 나란히 보여 주고, `n` 편집기는 **F⁰(raw) plan**으로 채우며, `saw_f0`와 `endorsed`를 기록한다. §3.5b의 rescue/regression은 gold 출처가 컴파일러와 독립인 트레이스(dataset gold, 또는 `saw_f0=true`인 인간 라벨)에서만 계산하고 출처별로 층화한다.

**화면(제안 4의 키보드 큐).** `traces.html`의 목록이 라벨 큐가 된다: `.seg` `unlabelled | invalid only | wrong only | all`(P2; `changed`는 P4에서 `compare_runs`가 오면 활성화, `parent_run_id` 없는 런·채팅 세션에서는 비활성), 진행 카운터. gold 없는 채팅 트레이스에서는 "wrong only"가 라벨 전까지 검증 실패만 뜻하므로 세그먼트 라벨을 `invalid only`로 표시한다. 키: `j/k` 이동, `y` 정답, `n` 오답(F⁰ plan으로 채워진 expected 편집기, 분류 evidence의 인자에 커서), `u` 불확실, `o` 순서 민감, `1..9` evidence 기반 제안 칩(별칭표 히트 `거실→living`, enum 값, 기본값), `Enter` 커밋+다음, `z` 되돌리기(=supersedes 행 추가), `g` raw JSON, `?` 도움말. 같은 판정 바가 `chat.html` 결과 카드에 붙는다.

**라벨러 신원과 일치도.** 라벨러는 한 명이고 규칙·모델도 같은 사람이 고르므로 라벨러 간 일치도는 정의되지 않는다. 대신 무작위 10%를 1주 이상 지나 새 `label_batch_id`로 재라벨해 자기 일치도 κ를 `analyzer_label_store.md` Observation에 보고하고, 자기 불일치 family는 내보내기에서 제외한다(명제 8의 의미 잡음 완화).

**학습 데이터(교정 SFT).** `ganglion/lm/synth/labels.py` [신규] `examples_from_labels(labels, traces, catalog, *, zones=('train',), include_correct=False) -> list[SynthExample]`(strategy=`human_label:<verdict>:<tool>`, `expected_dsl`는 `json.dumps(plan.to_jsonable(), sort_keys=True, ensure_ascii=False)`로 `pipeline.py:169-171`과 동일 정규화) → `synth.pipeline.write_jsonl`로 `runs/labels/<catalog_id>/<fingerprint>/human_sft.jsonl`. `cat synth.jsonl human_sft.jsonl > augmented.jsonl` 후 `train_lora`는 무수정. incorrect 라벨은 family 해시로 train/dev를 결정적으로 나눠 dev 쪽은 `hard_pool.jsonl`(§4 B4)에만 들어가고 절대 내보내지 않는다. pytest: `release`·`dev`·`unassigned` family 행은 어떤 내보내기에도 들어가지 않고 모든 행이 `parse_json_dsl` 왕복을 통과한다. **`human_dpo.jsonl`은 이번 사이클에 만들지 않는다.** 인간 정규형 문자열(chosen) 대 모델 raw(rejected)는 키 순서·공백·이스케이프 토큰이 log-ratio를 지배하는 off-policy 쌍이고(`docs/pipeline_formalization_impl.md:517`), ~50 라벨 × ~15% 오답 ≈ 8쌍은 논문이 이미 4쌍으로 이득 없음을 보고한 규모다(`ganglion_mlsys_draft.md:296`). 선호 최적화가 필요해지면 `lm_finetune.md:30-34`의 규칙대로 **현재 정책에서 N개를 샘플링**해 인간 gold로 `graded_score` 채점해 쌍을 만들고, ≥200쌍·≥3 seed 전에는 어떤 DPO 수치도 보고하지 않는다(미래 `finetune/dpo.py`). refine.md의 "RLHF"는 보상 모델이 아니라(`lm_finetune.md:50-51`) 교정 SFT로 구현한다는 문장을 `lm_label_dataset.md`에 명시한다.

**git 정책(완결성 심사 반영).** `runs/labels/`(zones, 내보내기, hard pool)는 항상 커밋. `runs/traces/**`는 전부 커밋 대상이되, 콘솔 세션 샤드는 `export-labels`가 참조하거나 어떤 매니페스트가 `parent_run_id`/`labels_used`로 가리킬 때 커밋한다 — `tests/test_run_refs.py` [신규]가 커밋된 매니페스트·내보내기가 참조하는 모든 경로의 존재를 검사하고, 참조되지 않는 세션 샤드는 `ganglion.console gc`가 정리 후보로 나열만 한다(삭제는 사람이). 그래야 P4의 ~50 라벨(iter1 학습 입력)이 완료 기준(경로 인용)을 만족한다.

**범위 밖.** 보상 모델, 콘솔에서의 학습 실행, 정책 샘플링 DPO 쌍(`dpo.py` 후속), 다중 라벨러 조정, 벤치마크 `Trace.expected_plan` 제거(v2 엄격 분리는 미결). **리스크.** 지문 X에서 만든 라벨은 계약 변경 후 진부 → 내보내기가 지문으로 필터·경고; 유효하지만 의미상 틀린 라벨은 탐지 불가(명제 8) → 자기 일치도 κ 보고.

### 3.5 R2.2 — 규칙 라이프사이클 (용어: 확장 = expand, 축소 = contract; "shrink"는 쓰지 않는다)

#### 3.5a 확장(expand): 제안 → 블라인드 결정 ledger → 검토된 이식

**흐름.** `POST /api/runs/{cat}/{run}/analyze`(= `python -m ganglion.console analyze`)가 기존 프리미티브를 순서대로 호출해 **스펙된 경로에만** 쓴다: `classify_traces(golds=resolve_gold)` → `classified.jsonl`; `synthesize_rules(golds=)` → `proposed_patches.jsonl` + `.summary.json`; `correction_attribution`(3.5b) → `corrections.jsonl` + `corrections.summary.json`(retire 후보는 `RulePatch(operation='retire_rule')`로 같은 `proposed_patches.jsonl`에 추가); `summarize/write_report` → `summary.json`, `report.md`. 각 단계가 선언된 이벤트(`analyzer.failure.classified`, `analyzer.rule.proposed`, `analyzer.correction.attributed`, `analyzer.metrics.summarized`)를 런의 `events.jsonl`에 남긴다. B1의 fixture와 precision은 50케이스 API 런이 아니라 **500케이스 전체 샤드**(rules 클라이언트 오프라인 + vLLM 베이스)에서 만든다 — `min_failure_count=5` 아래 50케이스 런은 제안 0–3개라 precision이 한 자릿수에서 추정된다.

**레코드.** `ganglion/analyzer/decisions.py` [신규] frozen `PatchDecision(decision_id, patch_id, catalog_id, run_id, catalog_fingerprint, stage∈{blind, after_preview}, decision∈{accept, hold, reject, retire}, reason, decided_by, time_to_decide_ms, decided_at)` → `patch_decisions.jsonl`(추가 전용, patch·stage별 최신 우선), `POST /api/patches/{patch_id}/decision`, 이벤트 `analyzer.patch.decided`. **블라인드 2단계**: 카드는 `blind` 결정이 기록되기 전에는 미리보기(예상 rescue/regression)를 숨기고, 이후 선택적으로 `after_preview` 결정을 받아 둘 다 보고한다(제안기가 결정을 앵커링하는 문제). 이식은 `POST /api/patches/{patch_id}/ported {commit_sha}`로 **명시적 참조**를 남겨 `applied_in`을 확정하고, `describe()` diff는 `detected_in` 힌트만 준다 — 손으로 독립 작성한 별칭과 수락된 패치를 구분할 수 없고, `set_default`의 술어 이식은 `describe()`가 존재 여부만 기록하므로 감지 불가이기 때문이다(alias/strip/extend_argspec/값 있는 default만 감지; `analyzer_patch_decision.md`에 명시). `factory_pipeline.md:34`의 "human approval signal observed on the event bus"는 어떤 Contract.event 절에도 선언된 이벤트가 없고, 같은 문서는 이를 외부 `contract.catalog.published`/새 `factory.pipeline.start`로 사상한다(101, 122행) — 이 제안의 `analyzer.patch.decided`가 그 자리에 들어가는 선언이다.

**accept는 아무것도 변경하지 않는다.** 빌트인 카탈로그는 Python 모듈이고 `rules.py:22-24`는 "NEVER mutates a Catalog or ToolSpec". accept = *승인됨, 이식 대기*. 카드에는 payload에서 파생한 편집 힌트(`EnumArg.aliases += {...}`, `strip_unknown_args=True`, `defaults_when_missing += (arg, default, <predicate hint>)`)를 보여 주고, Phase 3의 순수 함수 `ganglion/contract/patch.py:apply_patch(catalog, patch) -> Catalog` [신규](`dataclasses.replace`; `add_alias/set_default/enable_strip_unknown_args/extend_argspec(RawArg)/retire_rule`만 지원, `add_prompt_correction/ESCALATE`는 `PatchNotApplicableError`)로 **미리보기 카탈로그**를 만들어 저장된 raw를 재파싱하면 "예상 rescue/regression"을 붙일 수 있다(v2 `ImprovementProposal`의 기대 효과·불확실성; 블라인드 결정 후에만 노출). 실제 이식은 여전히 검토된 코드 편집이다. **`auto_apply`의 의미(모순 정리):** factory는 이번 사이클에 `auto_apply`를 *읽는다* — `False`(기본)면 `classified.jsonl`/`proposed_patches.jsonl`을 반복마다 쓰고 `pending_patches`로 정지하는 분기만 구현하고, `True` 분기는 `apply_patch`+게시가 없으므로 `NotImplementedError`로 fail loud한다. 보고되는 실험은 모두 `False`이므로 논문의 "proposes, does not apply" 경계는 유지된다. overlay 로딩·프로그램적 게시는 없다.

**화면.** `rules.html` 카드 레이아웃 유지, 데이터 모델을 `RulePatch.to_dict()`로 교체(operation · target_tool · source_failure_type · confidence/failure_count/support_share · `example_trace_ids` 링크). matcher가 없는 7개 실패형(NO_FAILURE 제외)은 "계약 패치 불가 → 라벨 후 재학습" 카드로, `ESCALATE` 카드는 Apply 대신 **"라벨 큐로 보내기"**(예시 트레이스를 데이터 엣지로). 키 `a/h/r/t/Enter`, `Hold all` 기본.

#### 3.5b 축소(contract): F⁰/Fᴷ 귀속 → 통계적 흡수 판정 → retire

**구성요소.** `ganglion/analyzer/corrections.py` [신규]: `strip_hooks(catalog, kinds) -> Catalog`는 `dataclasses.replace`로 요청한 hook 종류를 뺀 **새 frozen 카탈로그**를 만든다(복사, 변경 아님). **kinds는 셋뿐**: `defaults_when_missing`, `strip_unknown_args`(+`default_strip_unknown_args`), `prompt_correction`(단일 ablation은 replace 없이 `parse_json_dsl(raw, prompt=None)`으로 얻는다 — `catalog.py:161`). `custom_validator`는 제외한다: 정의 6은 F⁰에서 Correct만 항등으로 두고 Validate/Normalize는 유지하는데, `_validate_create_scene`(iot_light.py:259-291)은 중첩 `set_light` 검증과 `SCENE_ALIASES` 정규화를, HA의 `_make_targeted_validator`(home_assistant.py:106-124)는 `_has_target` 검사를 품고 있어 이를 빼면 별칭 scene 전부가 "validator rescue"로, 무타깃 호출이 가짜 regression으로 잡힌다. 각 kind는 정의 13에 따라 **보수적/재작성**으로 태그한다: `strip_unknown_args`는 보수적, `defaults_when_missing`은 대상 인자가 `required_arg_names()`에 있을 때만 보수적(선택 인자를 채우면 받아들여진 구조를 바꾼다), `prompt_correction`은 재작성. `correction_attribution(catalog, trace, gold)`는 **`attempts[0]`만** 재파싱한다(모델 단독 F⁰ vs Fᴷ; native 클라이언트는 tool_call 목록을 `{"calls":[…]}`로) — 마지막 시도는 Fᴷ의 오류 메시지가 되먹임된 산물이라 F⁰ 시스템도 F⁰ 모델도 아니며(정의 25), repair는 `summary.json`의 `repair_*` 통계로 따로 본다. `prompt`는 반드시 실어 보내고, `attempts[0]`이 없는 트레이스는 세지 않고 `unattributable`로 표시한다(테스트). 출력 `{f0_plan, fk_plan, rescued_by, regressed_by, necessary_hooks, gold_origin}`; 런별 `corrections.summary.json = {by_gold_origin{dataset|human_saw_f0: {em_f0, em_fk, rescue, regression}}, by_hook{(tool, kind, conservative|rewriting): {necessary, rescues, regressions, n_active}}, shared, unattributable}`. 보수적 버킷은 `regression == 0`을 pytest로 단언한다(명제 6 ii; 별칭 없는 scene 픽스처에서 F⁰==Fᴷ도 단언). 여러 hook이 동시에 필요한 경우는 `shared`로만 센다. 이것이 명제 6(ΔEM = Rescue − Regression)의 채택 기준이자 `corrections_summary.json` 한 사례의 일반화다.

**retire 후보 판정(통계 보강).** 이전 런 A와 재학습 런 B에 대해 다음을 모두 만족할 때만 축소 패널에 올린다: (i) B에서 해당 hook이 *활성*인 케이스(F⁰≠Fᴷ) 수 `n_active_B ≥ 30`; (ii) `rescues_B = 0`이고 rescue율의 Clopper–Pearson 95% 상한 `1 − 0.025^{1/n_active_B} < τ`(기본 τ = 10%, 즉 n ≥ 36; 0/5 같은 표본은 상한 ≈ 52%라 무의미); (iii) `rescues_A > 0`; (iv) 정의 28의 흡수 조건을 비열등성으로: `EM⁽⁰⁾_B − EM⁽ᴷ⁾_A ≥ −δ`(δ = 1pp)의 짝 부트스트랩 CI 하한이 −δ 이상이고 B가 ≥3 학습 seed에서 같은 방향. 하나라도 못 미치면 패널은 "insufficient evidence"만 보여 주고 "retire candidate"라 부르지 않는다. gold 커버리지 50% 미만 런에서는 패널을 숨긴다. 후보는 `RulePatch(operation='retire_rule', target_tool, payload={hook_kind, arg?}, source_failure_type=FailureType.NO_FAILURE, evidence={n_active, rescues_A, rescues_B, ci95_upper, em_delta_ci})`로 `rules._make_patch_id`를 써서 발급되어 `proposed_patches.jsonl`에 들어가므로 `PatchDecision.patch_id`에 결합된다(모순 정리). 사람이 `retire`를 기록하면 제거 역시 검토된 편집이다. 논문의 일화("v1에서 19건 구제, v2에서 0건", 292행)가 CI 있는 열이 된다. **한계.** 귀속 단위는 `(tool, hook 종류)`까지 — `_chain` 안의 개별 correctors는 이름이 없어 더 세밀한 귀속은 `CorrectionRule` 명명 + `parse_json_dsl_traced`(Trace에 `correction_fires` 추가)라는 Module 3 후속 과제다.

**건드릴 모듈.** analyzer(corrections, decisions, rules `golds=`/`retire_rule`), contract(Phase 3의 `patch.py`), factory(`422-426` TODO 충족, `auto_apply` 읽기 분기), web(rules.html). **범위 밖.** 자동 적용·overlay 로딩, hook 명명 리팩터링, 7개 미커버 실패형의 새 matcher, 카탈로그 교차 패치 이전, custom_validator 안의 정규화를 분리하는 Module 3 태스크. **리스크.** 단일 종류 ablation은 상호작용 hook을 과소 귀속(`shared`로 보고); `analyzer_rule_synthesis.md:139`의 "Spec only" 상태는 같은 PR에서 정정.

### 3.7 측정 프로토콜 — `factory_measurement_protocol.md` [신규 스펙]

§8의 주장이 성립하려면 P2 착수 전에 다음을 스펙으로 고정한다.

1. **블라인드 결정**: 패치 결정은 미리보기 전 `blind` 단계가 필수, `after_preview`는 선택; precision/recall은 두 단계 모두 보고(§3.5a).
2. **F⁰/Fᴷ 나란히 라벨링**: F⁰≠Fᴷ 카드에서 `saw_f0`·`endorsed` 기록; rescue/regression은 gold 출처별 층화(§3.4, §3.5b).
3. **임베딩 family 존**: template_id/최근접 cosine으로 family, 결정적 존 배정, `unassigned` 제외, `leakage_rate` 보고(§3.4).
4. **분리된 dev pool**: `hard_pool` = dev 존 오답 라벨, 절대 내보내지 않음, `compare_runs`가 `pool ∩ train = 0`을 검사(§4 B4).
5. **P4 2-arm 설계 + MDE**: (a) synth-only 어댑터, (b) synth+`human_sft` 어댑터, 같은 학습 seed·같은 디코딩; headline은 (a)↔(b) 짝 부트스트랩 CI. n=500, EM≈0.9에서 단일 비율의 95% CI 반폭 ≈ 2.6pp(≈13 케이스)이므로 사전 계산한 MDE와 필요한 오답 라벨 수 `N_required`를 이 스펙에 적고, 라벨이 미달이면 P4는 "인프라 검증"으로만 보고한다. iter0(vLLM 베이스)은 참조 행이며 Δ(iter0→iter1)을 라벨 효과라 부르지 않는다.
6. **디코딩 블록과 metric_kind**: 매니페스트에 기록, `compare_runs`는 동일할 때만 비교(§3.6).
7. **최소 n 규칙**: retire 후보 `n_active ≥ 30`·CP 상한 < τ·≥3 seed(§3.5b); `mean ± sd`는 n ≥ 3; precision은 `n_proposed`와 함께만 보고; DPO 수치는 ≥200쌍·≥3 seed 전에는 보고 금지.
8. **operator label space**: proposer precision·recall은 `factory_phase2_plan.md §17.2`의 7행 스택(`(tool, kind)` 단위로 표현 가능)에 대해; BFCL R1–R11(`post_correction.py:71-82`, gold 참조·RulePatch로 표현 불가)은 out-of-vocabulary로 별도 보고.

## 9. 미결 사항 / 적용하지 않은 반론

### 9.0 본문에서 확정한 결정 — 승인만 필요

- 카탈로그 정체성: `describe()` 해시 지문으로 이번 사이클을 가고 `Catalog.version`/`register()`/`contract.catalog.published` 발행은 Module 3 결정으로 미룬다(§3.2, §5).
- 게이트 문구: `contract_catalog.md:80`을 "게이트 이벤트 없이는 적용되지 않는다"로, `factory_pipeline.md:34`의 미선언 신호를 `analyzer.patch.decided`로 같은 PR에서 고친다(§5).
- 웹 UI 범위 반전: `research_vision_for_review.md:403`의 "CLI suffices"를 뒤집는 결정을 `console_operator.md`에 날짜와 함께 기록(§3.0).
- `LocalHFClient` 제외, vLLM LoRA 모듈이 유일한 로컬 경로(§3.1).
- `human_dpo.jsonl` 미생산, 교정 SFT만(§3.4).

### 9.1 사용자가 결정해야 할 것

1. **이음새 확정.** "이벤트 = 런 디렉터리의 ledger 행, 전역은 파생 색인"을 v2 bus-vs-ledger 질문의 날짜 있는 해소로 기록할지, 아니면 콘솔-국소 로그로 두고 질문을 열어 둘지.
2. **anchor 전환 범위.** `registry/`·`runtime/` 패키지 생성을 미루고 lm/analyzer/console에 두는 이 제안을 승인할지; 전환 시점의 트리거(다중 프로세스 워커 필요 시 SQLite).
3. **gold 배치.** 하이브리드(벤치마크는 `expected_plan`, 인간은 `labels.jsonl`) vs v2 엄격 분리(트레이스 저장소 이전 필요).
4. **accept 의미의 다음 단계.** "승인됨·이식 대기 + 검토된 코드 편집"(현행) 이후 P3의 `apply_patch` 기반 overlay 로딩을 언제 허용할지.
5. **서버 스택.** stdlib `ThreadingHTTPServer`+단일 writer(권고) vs FastAPI+SSE(스트리밍이 실제 요구될 때만).
6. **문법 마스크 실험의 필요성.** vLLM structured output으로 `lm/grammar.py` 실험을 대체할 수 있으면 `lm_grammar_mask.md`의 XGrammar 경로를 유지할 이유가 있는지.
7. **순서 정답.** IoT/HA 카탈로그에서 위치 민감 동등성을 유지하고 `order_sensitive`를 라벨 플래그로만 둘지, `multi_tool` 합성 전략 태스크를 별도 발주할지.
8. **라벨러 신원과 존 예산.** `GANGLION_LABELER` 별칭(인증 없음)으로 충분한지; 카탈로그별 `release` 라벨 예산; incorrect 라벨의 train/dev 분할 비율(`train_share`) 기본값; 두 번째 라벨러 확보 가능성.
9. **git 정책.** `runs/labels/` 항상 커밋, 참조된 콘솔 세션 샤드만 커밋(`tests/test_run_refs.py`), `runs/ledger/index.jsonl` gitignore — 승인 필요.
10. **레거시 백필.** `runs/factory_bfcl` Phase 1–3 타임라인을 loops.html에 보이게 할 이전 태스크를 발주할지(스크립트가 제거된 패키지를 import하므로 포팅 필요).
11. **retire 임계값.** τ(기본 10%)·δ(1pp)·`n_active ≥ 30`·seed ≥ 3을 카탈로그별로 조정할지.
12. **P4 라벨 예산.** `N_required`가 P4 기간 안에 확보 불가하면 P4를 인프라 검증으로 격하하는 데 동의하는지.

### 9.2 적용하지 않았거나 다르게 적용한 반론과 이유

1. **미검증 plan을 `Trace.plan`에 넣자는 대안(엔지니어링 #1의 두 번째 선택지).** 채택하지 않음 — `plan is None`이 `metrics.exact_match`(74-78)와 taxonomy의 실패 신호이므로 `raw_plan` 필드를 새로 둔다(§3.0b-2).
2. **라벨 API 경로를 `/api/runs/{cat}/{run}/traces/{trace_id}`로 바꾸자는 안(엔지니어링 #4).** 경로는 유지하고 요청 본문에 `(catalog_id, run_id)`를 실어 샤드를 직접 열게 했다 — 같은 효과이고 `api.js`의 자원 모델이 단순하다.
3. **전역 `runs/ledger/events.jsonl` 폐지(엔지니어링 #9).** 부분 적용 — 런 상관 이벤트는 런 디렉터리로 옮겼지만, 런이 없는 이벤트(`lm.model.registered`)를 위해 작은 `global.jsonl`은 남기고 전역 조회는 파생 색인으로 강등했다.
4. **P4 3-arm(+contrastive)(ML #9).** 2-arm으로 축소 — 이번 사이클에는 DPO 쌍을 만들지 않으므로 세 번째 arm은 `dpo.py` 착지 후의 일이다.
5. **retire 술어 예시 수치(ML #3: n ≥ 30, 상한 < 5%).** 그대로 쓰지 않음 — 0/30의 Clopper–Pearson 95% 상한은 ≈ 11.6%라 5%와 양립하지 않는다. τ = 10%(n ≥ 36 필요)를 기본으로 두고 9.1-11에서 조정을 묻는다.
6. **rules 클라이언트를 다중 호출로 확장해 `seed`에서 시연(완결성 심사).** 하지 않음 — rules 대역은 `iot_light_5` 단일 호출 regex이고 확장은 그 자체가 테스트 픽스처 변경이다. 대신 adversarial 5건을 seed에 포함해 정답 측 렌더와 라벨 경로를 시연한다(§3.3).
7. **`custom_validator` 안의 정규화 분리를 이번 사이클에(ML #4의 후반).** 후속 Module 3 태스크로만 명시 — ablation에서 제외하는 것으로 측정 오류는 막히고, 분리는 계약 의미 변경이라 이 제안의 범위를 넘는다.
8. **채팅 세션 간 "changed" 필터(완결성 심사).** 미정의로 남김 — family 기준 세션 간 비교는 `compare_runs`의 다음 반복이며 이번엔 비활성 표시만 한다.
