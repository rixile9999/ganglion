# PPT 구성안: 모델 크기와 DSL 복잡도에 따른 특화 성능 예측

**프로젝트:** Ganglion  
**작성일:** 2026-09-16  
**발표 시간:** 본문 14장, 약 15분 + 토의  
**상세 문서:** [연구계획서](dsl_specialization_research_plan.md)

## 발표의 중심 문장

> “새로운 MCP 명세가 주어졌을 때, 어느 크기의 모델을 얼마나 학습시키면 어느 정도의 정확도로 해당 DSL을 사용할 수 있는지 예측하려 합니다.”

발표는 문제 → 연구 질문 → 변수와 실험 → 예측 검증 → 생산 시스템의 가치 → 실행 계획 순서로 진행한다. 모든 슬라이드는 **확인된 사실 / 가설 / 실험 계획** 중 상태를 표시한다. 아직 없는 결과를 그래프로 만들어 실측처럼 보여주지 않는다.

## 슬라이드 1. 제목과 연구 질문 — 30초

**제목:** 모델 파라미터 규모와 DSL 복잡도에 따른 특화 성능 예측  
**부제:** MCP 특화 소형 모델 생산·업데이트를 위한 경험적 모델링  
**상태:** 연구 제안

**화면 내용**

- 입력: MCP tool spec.
- 질문: 어떤 모델을 얼마나 학습시켜야 하는가?
- 출력: 예상 품질·생산 비용·모델 선택.

**그림:** `MCP 명세 → DSL → 성능 예측 → 특화 모델` 4개 상자.

**발표 메모:** “소형 모델 하나의 높은 점수보다, 새 도메인에서 생산 결과를 예상할 수 있는 시스템을 만들고자 합니다.”

## 슬라이드 2. 지금 필요한 것은 모델 선택의 근거 — 60초

**핵심 메시지:** 같은 작은 모델이 모든 도구 집합에서 같은 성능을 내지는 않는다.  
**상태:** 문제 정의

**화면 내용**

- 새 서버가 들어올 때 모델 크기·데이터 양을 다시 탐색해야 한다.
- 명세가 바뀌면 기존 모델에 추가 학습할지, 더 큰 모델로 옮길지 결정해야 한다.
- 전 후보 학습·평가는 품질을 확인할 수 있지만 생산 비용이 든다.

**그림:** 서버 A/B/C마다 모델 후보를 반복 시험하는 과정과 비용 항목.

**발표 메모:** “Ganglion은 생산 절차를 자동화하고 있습니다. 이번 연구는 그 절차가 어떤 후보를 선택해야 하는지에 예측 근거를 주는 것입니다.”

## 슬라이드 3. 핵심 질문: 모델 규모 × DSL 복잡도 × 학습량 — 60초

**핵심 메시지:** 관계 전체를 모델링하고 새로운 DSL에 대한 예측을 검증한다.  
**상태:** 연구 질문

**화면 내용**

```text
의미적 성공률 = f(모델 크기, DSL 특징, 학습량 | 추론 구성·요청 분포)
```

- 모델: 총 파라미터 수와 학습 파라미터 수.
- DSL: 명령·인자·구조·표현·유사성.
- 학습: 도구당 예제, 토큰, 반복 노출량.

**그림:** 세 입력 묶음이 성공률·불확실성으로 연결되는 개념도. 수치 곡선은 사용하지 않는다.

**발표 메모:** “몇 개가 한계인지 한 숫자를 찾는 것보다, 모델을 키우거나 데이터를 늘렸을 때 결과가 어떻게 달라지는지 예측하는 것이 목적입니다.”

## 슬라이드 4. DSL의 크기를 무엇으로 측정할 것인가 — 75초

**핵심 메시지:** 도구 수가 같아도 학습해야 할 구조와 구별의 난이도는 다르다.  
**상태:** 측정 정의 제안

**화면 내용**

| 축 | 측정 예시 |
|---|---|
| 명령·문법 | 명령 수, 정규화한 생성 규칙 수 |
| 인자·제약 | 인자 수, 타입·enum, 조건부 규칙 |
| 조합 | 중첩 깊이, 호출 연결·결과 참조 |
| 표현·구별 | 명세 토큰 수, 명령 간 의미적 유사성 |

**그림:** 같은 구조를 공유하는 조회 도구 집합과 서로 혼동하기 쉬운 명령 집합의 예시. 예시는 실험 결과가 아닌 설명용으로 표시.

**발표 메모:** “단순한 토큰 길이와 의미적 복잡도를 구분하겠습니다. 초기에는 하나의 복잡도 점수로 합치지 않고 특징별 설명력을 보겠습니다.”

## 슬라이드 5. ‘소화한다’는 무엇을 뜻하는가 — 60초

**핵심 메시지:** 문법에 맞는 출력을 넘어 요청의 의미를 올바르게 실행해야 한다.  
**상태:** 평가 설계

**화면 내용**

1. 구문: 파싱·타입·범위 검증.
2. 의미: 올바른 명령·인자·실행 결과.
3. 일반화: 보지 않은 자연어와 인자/명령 조합.

**주 지표:** 전체 요청 중 의미적으로 올바른 DSL 변환 비율.

**그림:** 문법은 맞지만 다른 방의 불을 켜는 예시 → 의미 평가 실패. 기대 결과는 독립 평가기만 보유.

**발표 메모:** “컴파일 성공을 작업 성공으로 세지 않겠습니다. 1차는 단일 호출로 시작하고 조합 일반화는 별도 난이도로 추가합니다.”

## 슬라이드 6. 선행연구와 우리가 검증할 차이 — 75초

**핵심 메시지:** 특화·합성·간섭 연구를 생산 결과의 예측과 선택으로 연결한다.  
**상태:** 문헌 근거 + 차별화 가설

| 연구 | 연결점 |
|---|---|
| TinyAgent | 소형 모델의 도구 호출 특화 |
| TOUCAN | MCP 기반 데이터 합성 |
| Knowledge Capacity Scaling Laws | 통제 실험으로 모델 규모와 능력의 관계 분석 |
| Tool-space Interference | 도구 집합·스키마 특성의 영향 |

**강조 문장:** “미사용 DSL의 성능을 예측하고, 그 예측으로 생산 비용을 줄였는가?”

**발표 메모:** “이들 연구가 우리 가설을 입증한 것은 아닙니다. 특히 지식 저장 용량 결과를 도구 사용 능력에 그대로 적용하지 않겠습니다. 최초성은 추가 문헌 조사로 확인합니다.”

**슬라이드 출처:** [TinyAgent](https://aclanthology.org/2024.emnlp-demo.9/), [TOUCAN](https://arxiv.org/abs/2510.01179), [Knowledge Capacity](https://arxiv.org/abs/2404.05405), [Microsoft Research 발표 소개](https://www.microsoft.com/en-us/research/video/tool-space-interference-an-emerging-problem-for-llm-agents/).

## 슬라이드 7. 현재 자산과 다시 확보할 근거 — 60초

**핵심 메시지:** 실행 기반은 있으나, 새 주장을 위한 독립 평가를 다시 세운다.  
**상태:** 코드·저장된 산출물 확인

**화면 내용**

- 재사용 자산: 계약 컴파일, 데이터 합성, LoRA 학습, 평가·분석.
- BFCL 후처리에 평가 정답 접근: 후처리 점수를 운영 성능에서 제외.
- IoT의 템플릿·방해 도구 실험: 모든 명령을 대상으로 하는 평가로 확장.
- 현재 결과는 새 예측 연구의 결론이 아님.

**그림:** “기존 실행 기반”과 “독립 데이터·통제 실험·예측 검증” 두 묶음.

**발표 메모:** “후처리의 91.2%와 81.0%는 정답을 이용한 교정 결과입니다. 높은 수치를 출발점으로 주장하지 않고, 평가 경계를 먼저 정리하겠습니다.”

**근거:** [후처리 코드](../../runs/factory_bfcl/post_correction.py), [기존 BFCL 보고서](../factory_bfcl_phase3_report.md), [IoT 생성기](../../examples/iot_light/generate_dataset.py).

## 슬라이드 8. 첫 실험: 24개 조건으로 관계를 관찰 — 90초

**핵심 메시지:** 처음에는 소수의 요인을 통제하고 성능과 비용을 측정한다.  
**상태:** 실행 계획

| 축 | 파일럿 조건 |
|---|---|
| 모델 | 같은 계열 3개 크기: 0.6B·1.7B·약 4B 후보 |
| 명령 수 | 8 / 32 / 128 / 256 |
| 유사성 | 낮음 / 높음 |
| 학습 | 도구당 64개 예제를 초기 기준으로 제안 |
| 실행 수 | 3 × 4 × 2 = 24, seed 1개 |

**그림:** 행=모델 크기, 열=명령 수의 빈 행렬을 유사성 조건별로 배치. 셀은 “측정 예정”으로 표시.

**발표 메모:** “추가한 도구들도 실제 평가에 등장합니다. 24개는 파일럿이고, 본 실험은 seed 3개로 72회에 더해 독립 카탈로그와 학습량 변화를 측정합니다. 정확한 모델 체크포인트는 실행 전에 고정합니다.”

## 슬라이드 9. 무엇 때문에 성능이 바뀌었는지 분리 — 75초

**핵심 메시지:** 데이터 부족·문맥 길이·학습 방식의 영향을 모델 용량으로 오인하지 않는다.  
**상태:** 통제 설계

**화면 내용**

- 도구당 데이터 고정 ↔ 총학습 토큰 예산 고정.
- 같은 DSL의 전체 스키마 ↔ compact 표현.
- raw 모델 ↔ 문법 제약·교정을 포함한 시스템.
- 대표 조건에서 LoRA rank·학습량 증가 확인.

**그림:** 관찰된 오류에서 데이터/표현/학습/의미 혼동으로 이어지는 진단 가지.

**발표 메모:** “전체 데이터 수를 고정한 채 도구 수만 늘리면 도구당 예제가 줄어듭니다. 이 효과를 분리하지 않으면 관계를 잘못 모델링할 수 있습니다.”

## 슬라이드 10. 예측이 맞는지 어떻게 검증할 것인가 — 75초

**핵심 메시지:** 미사용 DSL에서 단순 기준선보다 잘 예측해야 한다.  
**상태:** 분석 계획

**화면 내용**

- 기준선: 모델 크기만 / 모델 크기 + 도구 수 + 학습량.
- 제안: 인자·구조·유사성·표현 특징을 추가한 예측기.
- 카탈로그 단위 분할, 모든 seed는 같은 분할에 배치.
- 평가: MAE, calibration, 구간 coverage, 선택 후 품질 미달.

**그림:** 예측 성공률-실측 성공률 산점도의 빈 축과 일치선. 실제 점은 측정 후 추가.

**발표 메모:** “멱법칙을 먼저 정하지 않고 단순 회귀부터 비교합니다. 새로운 명령 수와 새로운 서버, 다른 모델 계열의 예측은 각각 나누어 보고합니다.”

## 슬라이드 11. 실제 MCP와 대형 모델 비교 — 75초

**핵심 메시지:** 통제 DSL에서의 관계가 실제 환경에서도 유효한지 확인한다.  
**상태:** 외적 타당성 검증 계획

**화면 내용**

- 권장 목표: 6개 도메인·12개 서버, 개발 4 / 미사용 평가 8.
- 서버당 약 300개 독립 요청. 도구별 coverage 확인.
- 강한 API 모델 2종 및 특화 공개 모델과 품질·비용 비교.
- 실제 MCP 실행 결과 검증. API와 로컬 지연의 의미를 구분.

**그림:** 통제 DSL → 실제 MCP → 외부 벤치마크의 검증 단계.

**발표 메모:** “새 서버의 스펙으로 합성·학습하는 것은 허용하지만 최종 요청과 정답은 숨깁니다. 자원이 부족하면 4개 도메인·8개 서버로 줄이고 주장 범위도 조정합니다.”

**출처:** [BFCL](https://gorilla.cs.berkeley.edu/leaderboard), [MCP-Atlas](https://arxiv.org/abs/2602.00933). 외부 벤치마크의 평가 단위는 자체 단일 호출 평가와 구분.

## 슬라이드 12. 예측을 Ganglion의 생산 결정에 사용 — 75초

**핵심 메시지:** 설명 모델의 가치를 생산 비용 절감으로 검증한다.  
**상태:** 시스템 기여 가설

**화면 내용**

- 비교: 항상 큰 모델 / 전체 후보 탐색 / 도구 수 기반 / 제안 정책.
- 입력: DSL 특징과 품질 요구.
- 출력: 모델 크기·학습량·검증 후 다음 후보 선택.
- 지표: 최종 품질 미달률, 탐색 GPU 시간, API·운영 비용.

**그림:** `예측 → 후보 선택 → 학습 → 독립 검증 → 릴리스 또는 다음 후보`.

**발표 메모:** “예측이 낙관적이면 검증 단계에서 걸러지고 추가 비용이 듭니다. 그 비용까지 포함해 전체 탐색보다 유리한지 보겠습니다. 이 단계가 MLSys의 시스템 기여입니다.”

**출처:** [MLSys 2027 연구 범위](https://mlsys.org/Conferences/2027/CallForResearchPapers).

## 슬라이드 13. 업데이트로 확장 — 45초

**핵심 메시지:** DSL 변화에 따른 예상 성능을 다시 계산해 업데이트 결정을 지원한다.  
**상태:** 선택적 확장 계획

**화면 내용**

- 변화: 명령 추가·삭제, 인자 변경, 의미·기본값 변경.
- 선택: 기존 모델 / 추가 학습 / 전체 재학습 / 모델 확대.
- 측정: 복구 시간·비용, 기존 기능 회귀.

**그림:** `DSL v1 → v2 → v3` 아래에 예측과 실제 결과를 기록할 빈 칸.

**발표 메모:** “업데이트는 중요한 확장입니다. 다만 우선 새로운 DSL의 성능을 예측할 수 있다는 근거부터 확보하고, 일정이 허용할 때 연속 변경으로 확장하겠습니다.”

**출처:** [MCPEvol-Bench](https://arxiv.org/abs/2607.14642).

## 슬라이드 14. 자원·일정·미팅 결정사항 — 45초

**핵심 메시지:** 첫 결정은 24개 조건 파일럿의 범위와 독립 평가 책임이다.  
**상태:** 실행 제안

**화면 내용**

## 토의용 부록 A. 예상 질문과 답변

| 질문 | 답변 요지 |
|---|---|
| 결국 도구 개수에 따른 정확도 그래프 아닌가? | 명령 수만 사용하는 기준선과 비교하고, DSL 특징·학습량의 추가 예측력 및 실제 선택 이익을 검증한다. 추가 이익이 없으면 복잡한 모델을 채택하지 않는다. |
| 파라미터 수가 모델 능력을 대표할 수 있나? | 같은 계열에서 먼저 비교하고 사전학습·구조·학습 파라미터 차이를 기록한다. 인과적 용량 법칙이 아닌 조건부 성능 예측이다. |
| 스키마가 프롬프트에 있으면 암기 용량 실험이 아닌 것 아닌가? | 맞다. full-schema와 최소 명세 설정을 구분한다. 주 실험의 추론 구성을 고정해 스키마 적용 능력을 측정한다. |
| 합성 DSL만 잘 예측하는 것 아닌가? | 카탈로그 단위 분리와 실제 MCP 서버 전이가 필수다. 전이가 안 되면 주장 범위를 통제 DSL로 제한한다. |
| 문법 제약이면 구문 정확도가 이미 높아지지 않나? | 의미적 성공률을 주 지표로 두고 raw 결과와 문법 제약 결과를 분리한다. |
| 왜 단순 SFT와 비교하나? | 특화 학습 일반의 효과와 Ganglion의 표현·선택 방식의 효과를 분리하기 위해서다. |
| 3개 크기로 scaling law라고 할 수 있나? | 파일럿으로 관계를 관찰하는 수준이다. 본 연구는 성능 예측으로 표현하고, 더 많은 크기·계열 없이는 보편 법칙을 주장하지 않는다. |
| 예측 실패 시 운영 품질은 어떻게 보장하나? | 최종 릴리스 전 별도 검증을 수행하고 필요하면 다음 후보로 이동한다. 실패와 추가 탐색 비용을 모두 평가한다. |

## 토의용 부록 B. 기존 결과의 사용 범위

## PPT 제작 지침

- 슬라이드마다 제목을 포함해 핵심 메시지 하나, 본문 3~4개 항목을 기본으로 한다.
- 도식의 모델 크기·명령 수는 **실험 조건**, 그래프의 성능값은 **측정 결과**로 구분한다.
- 결과가 없는 그래프는 축·측정 계획만 제시한다. 가상의 정확도·속도 개선율을 넣지 않는다.
- 문헌과 기존 결과는 해당 슬라이드 하단에 직접 링크를 넣는다. 관련 연구의 범위를 과장하지 않는다.
- 자세한 변수·통계·분할·재현 정보는 연구계획서 또는 부록으로 넘긴다.
- 자료를 외부 공유할 경우 로컬 경로·계정명 대신 공개 가능한 artifact 경로로 교체한다.

## 1분 발표 요약

“Ganglion은 MCP 명세로부터 특화 소형 모델을 생산하고 업데이트하는 시스템입니다. 이번에는 모델 하나의 높은 점수보다, 파라미터 규모와 DSL 복잡도, 학습량에 따라 특화 성능이 어떻게 달라지는지 모델링하려 합니다. 명령 수뿐 아니라 인자 구조, 의미적 유사성, 표현 길이를 측정하고, 처음 보는 DSL에서 성능 예측이 맞는지 검증하겠습니다. 이후 예측을 모델과 학습량 선택에 사용해 전체 후보 탐색보다 적은 비용으로 품질 조건을 만족할 수 있는지 확인합니다. 첫 단계는 평가 정답을 사용하는 경로를 정리하고, 세 모델 크기와 네 명령 수, 두 유사성 조건으로 구성한 24개 파일럿을 실행하는 것입니다.”
