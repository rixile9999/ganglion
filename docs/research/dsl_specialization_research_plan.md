## 1. 연구 요약

Ganglion의 목표는 MCP 도구 명세로부터 특화 소형 모델을 생산·업데이트하고, 결과물의 품질과 시스템 비용을 대형 모델 및 기존 특화 방식과 비교하는 것이다.

이번 연구의 중심 질문은 **“모델의 파라미터 규모, DSL의 규모·복잡도, 학습량에 따라 자연어 요청을 올바른 DSL 프로그램으로 변환하는 성능이 어떻게 달라지는가?”**이다. 도구 개수의 절대 상한을 찾는 대신, 이 변수들의 관계를 경험적으로 모델링하고 새로운 DSL에서 예측력을 검증한다.

연구는 세 결과물을 목표로 한다.

1. DSL 특성과 모델 크기에 따른 성능·비용 측정 데이터.
2. 새로운 DSL의 특화 결과를 예측하는 모델과 불확실성 추정.
3. 예측에 근거해 모델 크기와 학습량을 선택하는 Ganglion 생산 정책.

예를 들어 새로운 MCP 서버의 명세가 주어졌을 때 “0.6B와 1.7B 모델을 각각 어느 정도 학습시키면 어떤 성공률과 비용을 기대할 수 있는가?”에 답하는 것이 목표다. 예측기의 유용성은 최종 품질뿐 아니라 모델 탐색에 사용한 GPU 시간과 API 비용으로 검증한다.

## 2. 연구 범위와 주장

### 2.1 주된 주장

> 일정한 모델 계열·학습 방식·요청 분포에서, DSL의 규모와 구조적·의미적 특성은 소형 모델의 특화 성능을 설명한다. 이 관계를 학습하면 새로운 DSL에 대한 모델·학습량 선택 비용을 줄일 수 있다.

이 문장은 **검증할 가설**이다. 현재 확보된 결과로 입증되었다고 주장하지 않는다.

### 2.2 용어

| 용어 | 이 연구에서의 정의 |
|---|---|
| MCP tool spec | 도구 이름·설명·입력 스키마 및 명시된 제약. 프로토콜 전체와 구분 |
| DSL | MCP 명세를 바탕으로 정의한 명령·인자·타입·조합 규칙과 그 표현 |
| 특화 | 특정 DSL과 요청 분포에 맞춰 모델을 미세조정하는 과정 |
| DSL을 소화하는 능력 | 새로운 자연어 요청을 의미적으로 올바른 DSL 프로그램으로 생성하는 능력 |
| 보편적 생산 | 새로운 서버에도 같은 생산 절차를 적용하는 것. 모든 미지 도구의 무학습 처리를 의미하지 않음 |
| 업데이트 | 서버 명세 또는 요청 분포 변화에 따라 특화 모델·계약을 갱신하는 과정 |

### 2.3 1차 연구와 확장 연구

- **1차:** 단일 호출을 중심으로 DSL 규모·복잡도와 특화 성능을 모델링하고, 실제 MCP에서 전이와 모델 선택을 검증한다.
- **확장:** 조합 일반화, 다단계 호출, 명세 변경 후 예측 갱신 및 재학습 정책.
- 장기 추론 전체, 모든 MCP 서버, 모델의 이론적 정보 용량에 대한 보편 법칙을 주장하지 않는다.
- DSL의 파싱·컴파일을 실제 도구 실행과 구분한다. 스키마 적합성만으로 작업 성공을 판정하지 않는다.

## 6. 변수와 측정 정의

### 6.1 모델과 학습 변수

| 기호 | 정의 | 기록·통제 방법 |
|---|---|---|
| `P` | 모델 총 파라미터 수 | 주 실험은 dense 모델의 같은 계열에서 비교. 계열·사전학습 차이를 명시 |
| `A` | 실제 학습 파라미터 수 | LoRA rank, 대상 모듈, 어댑터 파라미터 수를 별도 기록 |
| `D` | 학습량 | 예제 수, 도구당 예제 수, 학습 토큰 수, 반복 노출량 기록 |
| `B` | 학습 비용 | GPU 시간, wall time, 합성 API 사용량. 동일 `D`가 동일 연산량을 뜻하지 않음 |
| `R` | 표현·추론 구성 | 프롬프트, 문법 제약, 교정, retrieval, decoding, quantization을 버전으로 고정 |

모델 크기 차이만으로 인과적 용량 차이를 주장하지 않는다. 동일 계열도 사전학습 데이터·훈련량·구조 차이가 있을 수 있다. 다른 계열은 외적 타당성 검증에 사용한다.

### 6.2 DSL 크기와 복잡도의 특징 벡터

초기에는 복잡도를 하나의 자의적인 점수로 합치지 않고 `C = (N, G, A_mean, T, H, K, L, S)`로 표현한다.

| 특징 | 조작적 정의 | 주의점 |
|---|---|---|
| `N` | 고유 명령/도구 수 | 모든 명령에 학습·평가 요청을 배정 |
| `G` | 중복을 정규화한 문법 생성 규칙 수 | 단순한 명령 열거와 구조적 다양성을 구분. 완전한 자동 추출은 후속 구현 |
| `A_mean` | 명령당 인자 수의 평균·상위 분위수 | 필수·선택 인자를 구분 |
| `T` | 인자 타입·enum 선택지·조건부 제약의 분포 | 하나의 개수로 무리하게 합산하지 않음 |
| `H` | 명세의 최대·평균 중첩 깊이 | 실제 평가 요청이 사용하는 깊이도 별도 기록 |
| `K` | 프로그램의 호출 수·의존 깊이 | DSL이 허용하는 구조와 요청 난이도를 구분. 1차에는 단일 호출로 고정 |
| `L` | 명세 및 프롬프트의 토큰 수 | 공통 tokenizer 기준과 각 모델 tokenizer 기준을 모두 기록 |
| `S` | 도구 간 의미적 유사성 | 통제 생성 조건과 고정 embedding의 근접도 사용. 임베딩 점수 자체를 진실로 취급하지 않음 |

인자 값의 추론 난이도, 자연어 표현, 도구 호출 빈도, 출력 길이는 요청 분포 `Q`의 특징으로 별도 기록한다. 단순 복사와 계산·추론을 요구하는 인자를 섞어 DSL 효과로 해석하지 않는다.

### 6.3 종속 변수

- **주 지표:** 전체 요청 중 의미적으로 올바른 프로그램을 생성한 비율. 해석기 또는 실행 후 상태·결과 검증기로 판정하며 유효 출력만 분모로 삼지 않는다.
- **보조 지표:** 구문 유효성, 명령 선택, 인자 정확성, 학습에서 보지 않은 인자 조합·명령 조합에 대한 일반화.
- **운영 지표:** p50/p95 완료 지연, 목표 지연 내 성공 처리량, GPU 메모리, 합성·학습·평가·추론 비용, 사람 개입 시간.
- **거절 지표:** 실행해야 할 요청의 거절과 실행하지 말아야 할 요청의 호출을 분리. 무조건 거절로 오류율이 낮아 보이는 현상을 방지한다.

## 7. 예측 모델

기본 모델링 대상은 다음 조건부 성공확률이다.

```text
p_success = f(log P, DSL 특징 C, 학습량 D ; 모델 계열 F, 추론 구성 R, 요청 분포 Q)
```

성공률 곡면과 예측 불확실성을 추정한다. 특정 성공률의 등고선은 결과를 활용하는 방법이며, 연구 전체를 통과·실패 상한 탐색으로 축소하지 않는다.

### 7.1 비교할 예측기

1. 전체 평균·모델 크기만 사용하는 기준선.
2. `P, N, D`만 사용하는 단순 회귀.
3. DSL 특징을 추가한 정규화 로지스틱 회귀 또는 GAM.
4. 데이터가 충분하면 계층 모형·비선형 모형 추가.

상호작용은 `P×N`, `P×S`, `D×N` 등 소수의 사전 가설부터 시작한다. 멱법칙이나 단조성을 처음부터 정답으로 가정하지 않는다. 설명력을 위해 과도한 특징·자유도를 추가하지 않는다.

### 7.2 검증 방법

- **DSL 일반화:** 카탈로그 단위 train/validation/test 분할. 동일 카탈로그의 다른 seed 결과는 같은 분할에 둔다.
- **규모 일반화:** 측정한 명령 수 사이의 보간과 측정 범위 밖 외삽을 분리해서 보고한다.
- **모델 일반화:** 가능하면 별도 크기 한 개 또는 다른 모델 계열을 예측 평가에 사용한다.
- **실제 MCP 전이:** 통제 DSL에서 얻은 관계가 미사용 MCP 서버에서도 유효한지 확인한다.
- **지표:** 성공률 예측 MAE/RMSE, calibration, 예측 구간 coverage, 모델 선택 후 품질 미달률·추가 비용.

예측기 입력은 생산 전에 알 수 있는 특징을 원칙으로 한다. 몇 개의 probe 요청을 허용하는 설정은 별도 기준선으로 두고 probe 비용을 포함한다. 최종 테스트 정답에서 추출한 특징은 입력할 수 없다.

## 8. 실험 설계

### E0. 평가 기반 정리

- 정답을 읽는 후처리를 운영 경로에서 분리하고, 평가 정답은 별도 평가기에만 제공한다.
- 기존 원출력과 후처리 결과를 구분한다. 규칙·프롬프트 선택은 개발 데이터에서만 수행한다.
- 공식 BFCL 평가 경로와 현재 구현의 차이를 점검한다.
- 실행 가능한 버전, 모델 revision, 데이터·프롬프트 해시, seed를 기록한다.

### E1. 통제 DSL 파일럿

| 축 | 초기 설정 |
|---|---|
| 모델 | 현재 활용 가능한 0.6B·1.7B와 같은 계열의 약 4B급 후보. 정확한 체크포인트·라이선스·학습 조건은 실행 전 확정 |
| 명령 수 | `8, 32, 128, 256` |
| 도구 유사성 | 낮음 / 높음 |
| 학습량 | 도구당 64개 예제를 초기 기준으로 제안. 단일 호출 및 유사한 인자 구조로 고정 |
| 반복 | 1개 학습 seed·1개 카탈로그 표본으로 초기 24개 조건 |
| 평가 | 명령당 최소 20개 독립 요청. 전체 평균과 도구별 macro 평균을 함께 보고 |

24개 조건은 파일럿이며 통계적 결론을 내리는 본 실험이 아니다. 쉬운 조건에서 포화되거나 긴 명세가 context 한도를 넘으면 이를 기록하고 개발 단계에서 설계를 조정한다. context 초과·truncation은 별도 실패 원인으로 표시한다.

프로그램 의미와 기대 결과를 먼저 생성하고, 그에 맞는 자연어 표현을 독립적으로 만든다. 분할은 패러프레이즈 생성 전에 원래 의미 사례·템플릿 단위로 수행한다. 동일 의미 사례의 표현만 바꾼 문장이 train/test를 넘나들지 않도록 한다.

### E2. 본 실험과 원인 분리

- 파일럿의 24개 조건을 학습 seed 3개로 확장하면 **72회 학습**이다. 기존 파일럿 실행이 동일 프로토콜이면 재사용할 수 있다.
- 별도 카탈로그 표본을 대표 조건에 추가한다. 학습 seed 반복과 카탈로그 표집 반복은 서로 다른 변동으로 분석한다.
- 도구당 데이터 고정, 총학습 토큰 예산 고정, 대표 조건의 데이터 증가 곡선을 분리한다.
- 인자 수·중첩·조건부 제약은 대표 부분행렬에서 하나씩 변화시킨다. 전 축의 전체 조합을 실행하지 않는다.
- 같은 DSL에서 full schema와 compact DSL 표현을 비교한다. 명세를 최소화한 학습 내재화 설정은 별도 실험으로 표시한다.
- 주 모델링은 문법 제약·교정 없는 raw 결과로 시작하고, 문법 제약·배포 가능한 교정 결과를 별도로 측정한다.
- LoRA 학습이 한계로 의심되는 대표 조건에서는 rank·학습량을 변화시킨다. 가능한 경우 일부 작은 모델의 full fine-tuning을 진단 비교로 사용한다.

추가 실험의 위치는 파일럿·개발 데이터로 정하고 최종 평가 전에 고정한다. 성공하는 조건만 최종 보고하지 않는다. 3개 모델 크기만으로 보편적인 scaling law를 주장하지 않는다.

### E3. 실제 MCP 전이

**권장 목표:** 6개 도메인·12개 서버. 4개 서버를 개발에 사용하고 8개는 생산 절차·예측기 고정 후 평가한다. 최소 2개 도메인은 개발에 노출하지 않는다. 자원에 따른 최소안은 4개 도메인·8개 서버(개발 4 / 평가 4)이며, 주장의 범위도 함께 축소한다.

- 파일·문서, 데이터베이스, 개발 도구, 업무 관리, 검색·정보 조회, IoT 등 서로 다른 의미를 가진 집합을 구성한다.
- 새 서버의 스펙을 읽고 합성 데이터를 생성하는 것은 허용한다. 평가 요청과 정답은 학습·규칙·모델 선택에서 제외한다.
- 서버당 약 300개 독립 평가 요청을 목표로 하고, 충분한 도구별 coverage가 없으면 추가하거나 범위를 명시한다.
- 실제 MCP 호출과 상태·결과 검증을 수행한다. 상태 초기화·서버 버전·외부 데이터 snapshot을 고정한다.
- 서버마다 작성한 어댑터·평가기의 수와 사람 시간을 기록한다. 특화 생산 코드의 변경과 평가 환경 준비를 구분한다.

외부 타당성은 [BFCL](https://gorilla.cs.berkeley.edu/leaderboard) 및 [MCP-Atlas](https://arxiv.org/abs/2602.00933) 등의 고정 평가 집합으로 보완한다. 선택한 범주·부분집합과 평가 단위를 공개한다. MCP-Atlas의 최종 답변 평가와 단일 호출 의미 평가를 같은 지표로 합산하지 않는다.

### E4. 예측 기반 생산 정책

```mermaid
flowchart LR
    A[MCP tool spec] --> B[DSL 컴파일과 특징 추출]
    B --> C[후보별 성공률·비용 예측]
    C --> D[모델과 학습량 선택]
    D --> E[특화 학습]
    E --> F[별도 검증 집합 평가]
    F --> G[릴리스 또는 다음 후보]
```

비교 정책은 항상 큰 모델 사용, 후보 전체 탐색, 도구 개수 기반 선택, 제안 예측 기반 선택이다. 품질 기준은 개발 단계에서 결정한 후 고정한다. 예측 구간이 넓거나 검증에 실패하면 다음 후보로 이동하고 그 비용까지 포함한다.

독립 평가 DSL의 실제 후보별 결과를 이용한 사후 최적 선택은 평가용 oracle이다. 이를 온라인 정책 입력으로 사용하지 않는다. 선택 후 품질 미달률과 실행 가능한 최적 후보 대비 초과 비용을 함께 보고한다.

### E5. 업데이트 확장

기본 예측과 실제 전이가 성립하면 대표 서버 3~6개에 3~4회 변경을 적용한다. 명령 추가·삭제, 인자 변경, 의미·기본값 변경을 분리한다.

- 기존 모델 유지, 추가 데이터 + replay, 전체 재학습, 예측 기반 선택을 비교한다.
- 새로운 DSL 특징과 소규모 개발 관측으로 추가 학습·모델 확대 여부를 판단한다.
- 변경 기능 성공률, 기존 기능 회귀, 검증된 새 릴리스까지의 시간과 누적 비용을 측정한다.
- 새로운 의미를 검증하려면 새 버전에 맞는 기대 결과가 필요하다. 같은 구문에서 의미가 바뀐 사례를 포함한다.

## 9. 기준선과 공정성

| 비교 축 | 기준선 |
|---|---|
| 특화 자체의 효과 | 미학습 소형 모델 / 동일 데이터·학습 예산의 일반 SFT |
| 표현의 효과 | native schema / compact DSL. 의미 정보와 예시 제공을 맞춤 |
| 추론 최적화 | 문법 제약·교정·retrieval·캐시를 각각 기록하고 유무를 비교 |
| 실제 품질 기준 | 도구 호출 특화 공개 모델 및 서로 다른 제공자의 강한 API 모델 2종 |
| 생산 정책 | 항상 큰 모델 / 전체 탐색 / 도구 수만 이용 / 제안 예측기 |
| 업데이트 | 무갱신 / 추가 학습 + replay / 전체 재학습 / 제안 정책 |

학습·추론의 총 토큰, 최대 출력 길이, 재시도 예산과 실패 사례를 보고한다. 토큰 수·예제 수·GPU 시간의 동등성은 별개이므로 각 실험에서 무엇을 맞췄는지 명시한다.

API 지연과 로컬 지연 비교는 배포 시스템 전체의 비교다. 모델 계산 자체의 속도는 같은 하드웨어·서빙 조건에서 가능한 공개 모델끼리 비교한다. H100에서의 결과만으로 엣지 장치 성능을 주장하지 않는다.

## 10. 통계와 데이터 독립성

- 요청별 paired 비교와 함께 서버·카탈로그 단위 변동을 보고한다. 반복 seed를 독립적인 새 테스트 사례로 세지 않는다.
- 계층 bootstrap 또는 계층 모형으로 카탈로그·seed·요청의 종속성을 반영한다. 단순한 독립 이항 구간은 참고치로만 사용한다.
- 성공률 약 90%에서 독립 사례 500개의 단순 근사 95% 구간은 약 ±2.6%p다. 1%p 차이를 동등성 증거로 해석하지 않는다.
- 품질 조건의 예시로 95% 또는 대형 모델 대비 -2%p를 검토할 수 있지만, 파일럿 후 개발 데이터에서 적합성을 판단하고 최종 평가 전에 고정한다. 학회 요구 기준이 아니다.
- 학습 데이터, 개발용 피드백 데이터, 최종 테스트 데이터의 용도를 명시한다. 모델과 규칙을 반복 수정한 holdout은 개발 데이터로 재분류한다.
- 합성 자연어는 독립 샘플 검수로 의도 일치 여부를 확인한다. 구조 검증 통과를 의미적 정답으로 간주하지 않는다.
- 평가기가 준비되지 않은 서버·도구는 제외 이유와 비율을 기록한다. 실제 지원 범위를 공개한다.

아래 그림은 제작 계획이다. 아직 측정하지 않은 성능값으로 그래프를 만들지 않는다.

## 12. 자원과 예산

원화 1,000만 원을 상한으로 사용한다. 대화에서 함께 언급된 달러 금액과 동일하다고 가정하지 않는다. 아래는 견적이 아닌 배분안이며 H100 대여료가 별도로 들지 않는 조건이다.

| 항목 | 배분 상한 |
|---|---:|
| DSL 학습 데이터 합성·검증 API | 250만 원 |
| 대형 모델 비교·외부 평가 API | 250만 원 |
| 독립 평가 데이터 제작·사람 검수 | 200만 원 |
| MCP 환경·스토리지·외부 서비스 | 100만 원 |
| 재실험 예비비 | 200만 원 |
| 합계 | **1,000만 원** |

처음 24개 조건에서 건당 토큰·GPU 시간·실패율을 실측한다. 본 실험 72회와 추가 데이터/카탈로그/실제 서버 실험의 총시간을 그 결과로 산정한다. 72회는 전체 프로젝트의 실행 횟수가 아니다. 사전 단계에서 성능·비용을 확인하지 않고 전체 조합을 예약하지 않는다.

교사 합성 데이터를 모델 크기 간 공유해 비교를 짝짓고 API 비용을 줄인다. 장문·다단계 조건은 소규모로 먼저 측정한다. GPU 연산보다 독립 데이터 구축과 평가 환경 준비가 일정의 병목일 수 있다.
